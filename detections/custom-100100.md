# Custom rule 100100: password guessing on one account

**Status:** deployed on 2026-11-13 and fired once in a live test. Syntax was checked with `wazuh-analysisd -t` (exit 0) before the manager was restarted. Confirmed in the alert list: four 60122 alerts for failures 1 to 4, then 100100 at the 5th failure, then a 60122 for the 6th. 60204 did not appear.

## The rule

Added to `/var/ossec/etc/rules/local_rules.xml` as a second `<group>` block. The rule was drafted with help from an AI assistant. I reviewed it and can explain each line.

```
<group name="local,windows,custom,">
  <rule id="100100" level="8" frequency="5" timeframe="120">
    <if_matched_sid>60122</if_matched_sid>
    <same_field>win.eventdata.targetUserName</same_field>
    <description>Possible password guessing: 5 failed logons for one account within 2 minutes</description>
    <mitre>
      <id>T1110.001</id>
    </mitre>
    <group>authentication_failures,</group>
  </rule>
</group>
```

- `if_matched_sid 60122` counts the built-in single-failed-logon alerts.
- `frequency="5"` with `timeframe="120"`: 5 of them within 120 seconds.
- `same_field win.eventdata.targetUserName`: the failures must be against the same account.
- Level 8, below the built-in brute-force rule (level 10), so it acts as an earlier warning.
- MITRE T1110.001 (Password Guessing), tactic Credential Access.

## How it differs from built-in rule 60204

| | 60204 (built-in) | 100100 (mine) |
|---|---|---|
| Groups failures by | source address (`win.eventdata.ipAddress`) | target account (`win.eventdata.targetUserName`) |
| Threshold | 8 within 240 s | 5 within 120 s |
| Catches | one source hammering many accounts (spraying) | many sources hammering one account |

They cover different patterns, so they complement each other. I have not tested the 4 plus 4 scenario (4 failures for each of two accounts), where I predict 60204 would fire and 100100 would not.

## Test

- Date: 2026-11-13, on `win-victim`, throwaway account `testuser`, own VM only.
- Method: 6 failed logons about one second apart, using `Start-Process -Credential` with a wrong password.
- Result: rule 100100 fired at 12:39:01 Budapest time (11:39:01 UTC), followed by a plain 60122 at 12:39:02. Windows event record 13370 (event 4625) was among the matched events. `rule.firedtimes` was 1. 60204 did not fire, as expected for 6 failures against a threshold of 8.

## False positives I can think of

- A person who forgot their password and keeps guessing.
- Something automatic with a stale saved password, such as a mapped drive, a scheduled task or a phone mail app after a password change. It retries steadily and would trigger the rule repeatedly.
- Tuning ideas: exclude known service accounts, raise the threshold, or add a source field to separate people from machines.

## Limits

- It only sees failures grouped by account name. A slow attack spread over more than 2 minutes would not trigger it.
- In this lab every attempt comes from the VM itself, so source-address logic cannot be tested realistically.
